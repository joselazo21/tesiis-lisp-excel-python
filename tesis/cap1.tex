Este capítulo presenta los fundamentos teóricos necesarios para el desarrollo

\section{Lenguajes de dominio espec\'{\i}fico}
\label{sec:dsl}
% ---------------------------------------------------------------------------

Los lenguajes de programación de propósito general (GPL, del inglés
\textit{General-Purpose Language}) como C, Java o Python ofrecen flexibilidad
máxima, pero a costa de mayor verbosidad y menor expresividad dentro de
dominios concretos.  Un \textbf{lenguaje de dominio específico}
(\textit{Domain-Specific Language}, DSL) es un lenguaje diseñado para
expresar soluciones dentro de un dominio particular de problemas, ofreciendo
abstracciones que reflejan directamente los conceptos y patrones propios de
ese dominio~\cite{fowler2010}.

\begin{definition}[DSL, \cite{van-deursen2000}]
Un lenguaje de dominio espec\'{\i}fico es un lenguaje de programaci\'on o
especificaci\'on ejecutable que ofrece, mediante abstracciones apropiadas,
poder expresivo centrado en ---y normalmente restringido a--- un dominio de
problemas particular.
\end{definition}

Los DSL se clasifican según su relación con el lenguaje anfitrión en dos
grandes tipos~\cite{fowler2010,mernik2005}:

\begin{description}
  \item[DSL interno (embebido).] Se construye usando la sintaxis y las
    capacidades del lenguaje anfitrión.  No requiere herramientas de análisis
    léxico ni sintáctico propias: el programador usa el lenguaje anfitrión
    como plataforma y el DSL actúa como una biblioteca con vocabulario de
    dominio.  Common Lisp es especialmente adecuado para este enfoque gracias
    a su sistema de macros, que permite extender la sintaxis del lenguaje sin
    necesidad de un compilador externo.

  \item[DSL externo.] Define su propia sintaxis y requiere un lexer y un
    parser propios.  El DSL es un lenguaje independiente del anfitrión;
    ejemplos conocidos son SQL, \LaTeX{} y Matlab.  Este enfoque ofrece
    mayor libertad sintáctica pero implica un esfuerzo de implementación
    significativamente mayor.
\end{description}

El DSL desarrollado en este trabajo es \textbf{interno}: está escrito en
Common Lisp, sus formas son expresiones Lisp válidas y no requiere ningún
parser externo.  Los macros de Lisp actúan como el compilador del DSL,
expandiendo las formas del dominio en constructores de nodos del AST.

\section{\'Arboles de sintaxis abstracta y generaci\'on de c\'odigo}
\label{sec:ast}
% ---------------------------------------------------------------------------

% ............................................................................
\subsection{\'Arbol de sintaxis abstracta}
\label{ssec:ast-def}
% ............................................................................

Un \textbf{árbol de sintaxis abstracta} (AST, del inglés \textit{Abstract
Syntax Tree}) es una representación estructurada en forma de árbol del código
fuente de un programa~\cite{aho2006}.  A diferencia del árbol sintáctico
concreto (CST), el AST abstrae los detalles de la sintaxis concreta
---paréntesis, palabras clave, signos de puntuación--- y retiene únicamente
la información semántica relevante: la estructura lógica del programa~\cite{scott2015}.

Cada nodo del árbol corresponde a un constructo del lenguaje y sus hijos
representan los subcomponentes de ese constructo.  Por ejemplo, la expresión
\texttt{a + b} se representa como un nodo de suma con dos hijos: el nodo
del identificador \texttt{a} y el nodo del identificador \texttt{b}.

En el diseño del DSL presentado en este trabajo, el AST cumple el papel
central de \textbf{representación intermedia independiente del backend}.
El programador construye el AST mediante las formas del DSL; un backend
lo recorre y produce la salida deseada.  La elección del backend ---hojas
de cálculo, bases de datos, una API web, un documento HTML--- es ortogonal
al programa DSL: el mismo AST alimenta cualquier backend que implemente la
interfaz de compilación.

% ............................................................................
\subsection{Generaci\'on de c\'odigo}
\label{ssec:codegen}
% ............................................................................

La \textbf{generación de código} es el proceso que transforma el AST en
código ejecutable o en código fuente de otro lenguaje, preservando el
comportamiento descrito en el programa original~\cite{aho2006}.  El generador
recorre el árbol nodo a nodo, produciendo para cada nodo la representación
correspondiente en el lenguaje de destino.

Este proceso puede producir código en cualquier lenguaje destino, lo que hace
al AST una representación intermedia que desacopla el lenguaje de descripción
del lenguaje de ejecución.  En este trabajo, el backend implementado genera
programas Python para la biblioteca openpyxl; sin embargo, la misma
representación AST podría alimentar un generador alternativo que produzca,
por ejemplo, sentencias SQL o documentos HTML.

Cada nodo del AST en este trabajo es una instancia de una clase CLOS definida
con la macro \dsl{defclass*}.  Los nodos se dividen en seis familias:
\begin{enumerate}
  \item Nodos de estructura del workbook (\dsl{xl-workbook}, \dsl{xl-sheet},
    \dsl{xl-region}, \dsl{xl-table}).
  \item Nodos de expresión de celda (\dsl{xl-expr-column-ref},
    \dsl{xl-table-range}, \dsl{xl-expr-countif}, \dsl{xl-expr-if}, etc.).
  \item Nodos de navegación por filas (\dsl{xl-expr-previous-row},
    \dsl{xl-expr-next-row}, \dsl{xl-expr-first-row}, etc.).
  \item Nodos de cuantificación existencial (\dsl{xl-expr-exists},
    \dsl{xl-domain-rows}).
  \item Nodos de referencia cruzada entre hojas (\dsl{xl-expr-cross-sheet-ref},
    \dsl{xl-expr-cross-cell}, \dsl{xl-expr-collect-over}).
  \item Nodos de formato condicional y posicionamiento (\dsl{xl-style-rule},
    \dsl{xl-anchor}, \dsl{xl-nav}, \dsl{xl-sheet-fixed-expr}).
\end{enumerate}

Esta organización se describe en detalle en el capítulo~\ref{cap:dsl}.

\section{El lenguaje de programaci\'on Common Lisp}
\label{sec:lisp}
% ---------------------------------------------------------------------------

Common Lisp es un lenguaje de programación multiparadigma que combina los
estilos funcional, imperativo y orientado a objetos~\cite{steele1990}.  Fue
diseñado originalmente por John McCarthy en 1958~\cite{mccarthy1960} y
estandarizado como Common Lisp en 1994.  Su elección como plataforma de
implementación del DSL se justifica por su homoiconicidad y por dos
mecanismos fundamentales: los macros y las funciones genéricas.

\textbf{Homoiconicidad}: el código comparte la misma estructura que los
datos.  En Common Lisp, todas las expresiones son listas anidadas con
notación prefija: el primer elemento es el operador y los siguientes son
los argumentos.  Una llamada a función, la definición de una clase, una
iteración y una forma del DSL tienen exactamente la misma estructura
sintáctica.  Esta propiedad hace que el compilador pueda inspeccionar y
transformar el código del mismo modo que manipula listas de datos
ordinarias~\cite{graham1993}.  Los DSL internos se benefician directamente
de esto: las formas del DSL son listas ordinarias que los macros transforman
en código válido sin necesidad de ningún parser externo.

% ............................................................................
\subsection{Macros}
\label{ssec:macros}
% ............................................................................

Los \textbf{macros} de Common Lisp implementan metaprogramación: operan
sobre representaciones simbólicas del código fuente antes de su evaluación,
extendiendo el lenguaje sintácticamente~\cite{seibel2005}.  Un macro recibe
como argumento el código fuente ---representado como una lista--- y devuelve
código nuevo que sustituye a la forma original antes de la compilación.

La diferencia con una función ordinaria es temporal: una función se evalúa
en tiempo de ejecución; un macro se expande en tiempo de compilación.  Esta
distinción permite introducir nueva sintaxis y nuevas abstracciones sin coste
adicional en tiempo de ejecución.  Es esencial para implementar DSL internos
que se leen como vocabulario del dominio pero se compilan a estructuras de
datos eficientes.

En este trabajo, cada constructo del DSL ---\dsl{def-table},
\dsl{conditional-rendering}, \dsl{exists}, \dsl{nav}--- se implementa como
un macro que construye uno o más nodos del AST.  El programador escribe en
vocabulario del dominio; el macro transforma esa escritura en llamadas a
los constructores CLOS.

% ............................................................................
\subsection{Funciones gen\'ericas y CLOS}
\label{ssec:clos}
% ............................................................................

El \textbf{Sistema de Objetos de Common Lisp} (CLOS, del inglés
\textit{Common Lisp Object System}) introduce las \textbf{funciones
genéricas}: una interfaz común con múltiples métodos especializados según
las características de los argumentos~\cite{clos1988}.  El despacho dinámico
se realiza en función del tipo de los argumentos en tiempo de ejecución,
lo que separa la definición de la interfaz de sus implementaciones concretas.

Las funciones polimórficas se declaran con \dsl{defgeneric} y se especializan
con \dsl{defmethod}.  A diferencia de los sistemas de objetos convencionales,
CLOS soporta \textbf{despacho múltiple}: el método seleccionado puede
depender del tipo de varios argumentos simultáneamente, no solo del
``receptor''~\cite{kiczales1991}.

En este trabajo, CLOS cumple dos funciones.  Primero, las clases CLOS
representan los nodos del AST: cada tipo de nodo es una clase con slots que
almacenan sus atributos.  Segundo, la función genérica del backend
---\dsl{compile-excel-formula} en la implementación de demostración--- usa
el despacho múltiple para compilar cada tipo de nodo a la representación de
salida correspondiente, sin ninguna estructura \dsl{cond} o \dsl{case}
centralizada.  Añadir soporte para un nuevo tipo de nodo solo requiere
definir un nuevo \dsl{defmethod}; el resto del sistema no se modifica.

% ............................................................................
\subsection{La macro \texttt{defclass*}}
\label{ssec:defclass-star}
% ............................................................................

La notación prefija de Lisp y la ausencia de la distinción entre código y
datos hacen innecesario un lexer externo para construir el AST del DSL: cada
forma del DSL es directamente una lista anidada que un macro puede transformar
en un nodo del AST.  Para reducir el código repetitivo de definir clases CLOS
y sus constructores, el sistema define la macro \dsl{defclass*}, que genera
simultáneamente:

\begin{itemize}
  \item Una clase CLOS con nombre \dsl{clase-xl-\textit{nombre}}, donde
    cada slot tiene un accessor y un \texttt{initarg} del mismo nombre.
  \item Una función constructora \dsl{xl-\textit{nombre}} con argumentos
    por clave (\dsl{\&key}), que crea una instancia de la clase con los
    valores proporcionados.
\end{itemize}

\begin{lstlisting}[language=CommonLisp,
  caption={Implementaci\'on de defclass*.}]
(defmacro defclass* (class-name parents slots
                      &key (ctr-args-type '&key))
  `(progn
     (defclass ,(symb 'clase- class-name) ,parents
       ,(loop for s in slots
              collecting (expansion-del-slot s)))
     ,(make-constructor class-name slots
                        :argument-type ctr-args-type)))
\end{lstlisting}

Por ejemplo, la definición del nodo \dsl{xl-expr-if}:

\begin{lstlisting}[language=CommonLisp,
  caption={Ejemplo de uso de defclass*.}]
(defclass* xl-expr-if () (test then else))
;; genera:
;;   (defclass clase-xl-expr-if ()
;;     ((test :accessor test :initarg :test)
;;      (then :accessor then :initarg :then)
;;      (else :accessor else :initarg :else)))
;;   (defun xl-expr-if (&key test then else)
;;     (make-instance 'clase-xl-expr-if
;;       :test test :then then :else else))
\end{lstlisting}

Este patrón elimina el código repetitivo de definición de nodos y garantiza
que cada clase tiene una función constructora consistente con su interfaz
de inicialización.

\section{Hojas de c\'alculo y el formato \xlsx{}}
\label{sec:hoja-calculo}
% ---------------------------------------------------------------------------

El backend implementado en este trabajo produce archivos \xlsx{}, el formato
de Microsoft Excel basado en Office Open XML~\cite{ooxml}.  Los conceptos
siguientes son necesarios para comprender ese backend; no son centrales al
diseño del DSL, que es independiente de cualquier formato de salida.

Una \textbf{hoja de cálculo} (\textit{spreadsheet}) es una aplicación para
organizar, calcular y visualizar datos en una cuadrícula bidimensional de
celdas.  Cada celda puede contener un valor literal ---un número, una fecha
o una cadena de texto--- o una \textbf{fórmula}: una expresión cuyo
resultado se recalcula automáticamente cuando cambia cualquier celda de la
que depende~\cite{microsoft-excel}.

\begin{description}
  \item[Workbook (libro de trabajo).] Un archivo \xlsx{} que agrupa una
    o más hojas de trabajo.  Es la unidad de intercambio del formato
    Office Open XML~\cite{ooxml}.

  \item[Hoja de trabajo.] Una cuadrícula de celdas dentro del workbook,
    identificada por un nombre (p.~ej., \texttt{Defensas}).

  \item[Celda.] La unidad mínima de almacenamiento, referenciada por
    una dirección del tipo \texttt{B4} (columna~B, fila~4) o
    \texttt{\$B\$4} (referencia absoluta).

  \item[F\'ormula.] Una expresión que comienza con \texttt{=} y puede
    contener referencias a otras celdas, rangos y funciones predefinidas
    como \texttt{COUNTIF}, \texttt{COUNTA}, \texttt{SUM}, \texttt{IF} o
    \texttt{SUMPRODUCT}.

  \item[Rango.] Un bloque rectangular de celdas contiguas, expresado como
    \texttt{\$B\$4:\$F\$6} (columnas B--F, filas 4--6).

  \item[Formato condicional.] Un mecanismo que aplica estilos visuales
    ---color de relleno, color de texto, borde--- a las celdas de un rango
    cuando se cumple una condición evaluada en tiempo de apertura o edición
    del archivo.  Una \textbf{FormulaRule} es el tipo más general de regla
    de formato condicional: la condición es una fórmula arbitraria, lo que
    permite expresar condiciones que involucran otras hojas, otras celdas
    o funciones de agregación~\cite{openpyxl}.
\end{description}

La biblioteca \textbf{openpyxl} es la herramienta Python elegida para
producir archivos \xlsx{} en este trabajo.  Permite crear workbooks, escribir
valores y fórmulas en celdas, y definir \texttt{FormulaRule} que quedan
incrustadas en el archivo y se evalúan en Excel o LibreOffice Calc sin
necesidad de código adicional~\cite{openpyxl}.
